## 1. Objective & Scope

Phase 7 establishes a typed, reusable, provenance-aware road-network and road-segment data foundation for Suraksha Path. This layer enables the platform to associate genuine route polylines generated by the routing engine with identifiable physical road segments across Chennai.

### Key Architectural Tenet: Separation of Concerns
- **Phase 7 Role:** Geospatial modeling, authentic road-network ingestion, deterministic segment identification, spatial queries, and route-to-segment matching.
- **Strict Boundary:** No safety scoring, risk evaluation, crime predictions, or safe/unsafe labeling occur in this phase. Road geometry or classification alone is never treated as evidence of safety.

## 3. Data Model & Segmentation Approach

### Database Entity: `road_segments` (`RoadSegment`)
The relational schema in `backend/app/models/domain.py` defines:

| Column | Type | Description |
| :--- | :--- | :--- |
| `id` | `Integer` (PK) | Auto-increment primary key |
| `segment_code` | `String(64)` (Unique, Indexed) | Stable deterministic identifier (`SEG-OSM-W{way_id}`) |
| `source_feature_id` | `String(128)` (Indexed) | Upstream provider identifier (e.g. `way/24483756`) |
| `source_dataset` | `String(64)` | Provenance label (`OpenStreetMap`) |
| `road_name` | `String(255)` (Indexed) | Sourced road name (or `null` if unmapped) |
| `road_classification` | `String(64)` (Indexed) | Standard classification (`trunk`, `primary`, `secondary`, `tertiary`) |
| `from_node_id` | `String(64)` | Connectivity upstream node reference |
| `to_node_id` | `String(64)` | Connectivity downstream node reference |
| `start_lat`, `start_lng` | `Float` | WGS84 starting coordinate vertex |
| `end_lat`, `end_lng` | `Float` | WGS84 ending coordinate vertex |
| `length_meters` | `Float` | Great-circle (Haversine) length along coordinate vertices |
| `geometry_geojson` | `Text` | GeoJSON `LineString` format `{"type": "LineString", "coordinates": [[lng, lat], ...]}` |
| `source_metadata_json` | `Text` | Extensible JSON storing raw tags (lanes, oneway, maxspeed, surface, ref) |
| `created_at` | `DateTime` | Timestamp of ingestion |

### Identifier Strategy
1. **Source-Linked Identifiers:** Segment codes follow the format `SEG-OSM-W{way_id}` where `{way_id}` is extracted directly from the upstream OSM feature.
2. **Deterministic Hash Fallback:** For features lacking an upstream ID, SHA-256 fingerprinting of start/end coordinates generates a permanent identifier (`SEG-{hash[:12]}`), ensuring identifiers never change across application reboots or migrations.
3. **No Unnecessary Subdivision:** Existing OpenStreetMap ways represent natural intersection-to-intersection or homogeneous corridor segments; they are preserved intact without synthetic slicing.

## 4. Ingestion Pipeline (`RoadNetworkService.ingest_geojson_dataset`)

The ingestion pipeline in `backend/app/services/road_network_service.py` operates idempotently:
1. **Validation & Filtering:**
   - Validates feature geometry type (strictly `LineString`).
   - Validates coordinate bounds (latitude between -90 and 90, longitude between -180 and 180).
   - Rejects geometries with fewer than 2 coordinate points.
   - Requires valid `source_feature_id` or coordinates for code derivation.
2. **Geometric Normalization:**
   - Normalizes coordinates to standard GeoJSON `[[lng, lat], ...]`.
   - Computes total cumulative length in meters using spherical geodesic calculations.
3. **Idempotency & Duplicate Avoidance:**
   - Pre-checks existing `segment_code` records in the database.
   - Skips duplicate features without raising errors, returning an accurate summary.
4. **Ingestion Summary Metrics:**
   - `total_features_examined`
   - `imported_segments_count`
   - `skipped_duplicates_count`
   - `rejected_features_count`
   - `rejection_reasons`
5. **Startup Auto-Ingestion:**
   - During FastAPI application startup (`lifespan`), if the `road_segments` table is empty, `backend/app/data/chennai_road_network.json` is automatically ingested into the SQLite store.

## 5. Route-to-Segment Association Layer (`match_route_to_segments`)

When the routing engine produces a real route polyline, Suraksha Path determines which road segments were traversed:

### Algorithm
1. **Geodesic Tolerance Sphere:** Sets a configurable lateral proximity threshold (default: 35.0 meters).
2. **Vertex-to-Segment Projection:**
   - For every segment in the network, tests whether its vertices or midpoint project within the tolerance distance of any route step segment.
   - Uses perpendicular point-to-line-segment geodesic projection (Haversine).
3. **Sequential Traversal Ordering:**
   - Matches are indexed against the earliest route coordinate index where the segment was encountered.
   - Sorts matched segments into strict chronological order (`traversal_order`: 0, 1, 2, ...).
4. **Metrics & Unmatched Route Accounting:**
   - Calculates `matched_segments_count` and `total_matched_length_meters`.
   - Compares matched length to total route length, computing `coverage_ratio` (0.0 to 1.0).
   - Returns explicit accounting for routes traversing areas outside the ingested network (no false claims of full coverage).

## 6. Spatial Query Interfaces

The backend exposes high-performance spatial query endpoints:

| Endpoint | Method | Purpose |
| :--- | :--- | :--- |
| `/api/segments` | `GET` | Paginated listing with corridor, classification, and name search |
| `/api/segments/{segment_code}` | `GET` | Detail lookup by stable segment code |
| `/api/segments/bbox` | `POST` | Query segments intersecting geographic bounding box (`min_lat`, `min_lng`, `max_lat`, `max_lng`) |
| `/api/segments/near` | `POST` | Proximity query around coordinate with search radius |
| `/api/segments/match-route` | `POST` | Match an arbitrary polyline against road segments |
| `/api/segments/ingest` | `POST` | Repeatable administrative dataset ingestion |
| `/api/segments/provenance` | `GET` | Licensing, attribution, coverage, and provenance report |

## 7. Interactive Map Visualization (Phase 7)

In `frontend/src/components/map/InteractiveMap.jsx`:
- **Optional Toggle:** Road segment overlay is disabled by default (`road_segments: false`) to avoid map clutter.
- **Dedicated Badge:** A "Roads" badge in the map controls allows users to switch the overlay on and off.
- **Distinct Sourced Styling:** Sourced road segments are rendered in neutral cyan/slate (`#38bdf8`, weight 4) without fake risk colors or heatmaps.
- **Interactive Inspection:** Hovering highlights the segment; clicking opens an inspector card displaying road name, classification, stable segment code, length, and OpenStreetMap provenance.
